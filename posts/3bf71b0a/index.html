    1.复现Dr.MAS和C3实验

    C3环境中缺少MBPP+中的数据，项目在读取的时候错误的把读取字段，导致每行除了task_id和source以外返回的数据都是null，题目和代码等等内容都是空的。同时，项目还只检查文件的SHA256和manifest中的哈希一不一致，但是错误文件的哈希也能通过校验，就产生了这一个bug，有可能是作者用的模型太蠢了产生了幻觉，维护仓库的时候造成的乌龙。同时，作者提供的MATH训练集和测试集中有一道完全相同的题，会导致数据泄露，测试结果不可靠。我又反馈了这一问题也重新得到了回复。

    Dr.MAS

    4B的sharing和non-sharing两个训练作业之前在大数据平台上跑完了，都是814 step（total_epochs=2），sharing跑了60.6小时，non-sharing 71.4小时。两个eval作业也出结果了，所以这周终于可以拿avg@16/pass@16跟论文中的表格直接对比数据。

    1.1 test_score指标

    翻了verl/trainer/ppo/ray_trainer.py:884才搞明白，test_score = np.mean(rewards)是按agent行平均的，一条轨迹里Solver和Verifier各占一行，Solver被reject还会再来一行，所以分母是30（AIME‘24的题目数量）×2~3。需要用compute_pass_at_k_and_avg_at_k算一下。

    1.3 差异来源

    我最开始怀疑论文是不是没取完整814步的结果，原文从头到尾确实没写训了多少步，appendix里只有超参没有step数。但是官方脚本中的src/examples/drmas_trainer/run_math.sh里total_epochs=2是写死的，也没有total_training_steps上限。所以814 step就是官方配方跑满的结果，作者跑同一个脚本也是814。而且如果作者他们只训到200步，六项应该整体偏低，不会出现non-sharing逐项吻合、还有两项比我高的情况。

    真正的原因应该是AIME’24只有30题，噪声太大。用我自己训练中的val数据就能量化，同一个模型能力水平下（step≥500的33次评估）

    AIME24  avg@1:  均值47.7  标准差6.2  范围36.7~60.0
overall avg@1:  均值62.9  标准差2.2

    同一个模型、同一个数据集，光靠采样随机性AIME’24就能在36.7和60.0之间来回跳23个点。+12.2大概1.5~2σ，在可接受的范围内。

    btw，我感觉AIME’24只有30题还被当主指标用就有点不是特别convincing，论文里那些±几个点其实基本都有比较大的噪声干扰。

    1.4 episode/length恒为1

    训练曲线里episode/length的min/max/mean三条线814步一动不动全是1，而max_loop_num=2，一开始以为Solver↔Verifier的精化循环根本没进过第二轮。于是我让Claude查了一下代码发现agent_system/environments/env_package/math/envs.py:23中定义了

    def step(self, action: str):
    done = True  # always done after one step

    agent_system/multi_turn_rollout/rollout_loop.py:444

    for _step in range(self.config.env.max_steps):
    text_actions, buf = self.multiagent_orchestra.run(...)   # Solver↔Verifier整个循环在这一行里面
    next_obs, rewards, dones, infos = envs.step(text_actions)
    episode_lengths[active_masks] += 1                        # 只数外层env step
    if is_done.all(): break                                   # math env第一步就done

    所以episode/length数的其实是外层环境交互轮数，跟精化轮数没关系。math env一步就done，这个值恒为1是必然的。它只在search任务里才有意义，那边env.max_steps=max_turn=4，run_math.sh压根没设env.max_steps。

    所以Solver↔Verifier循环本身是在正常跑的，在math_orchestra.py的run()里面。max_loop_num=2展开之后，loop 0 Solver跑全部，Verifier审全部，更新approved_vector；loop 1 Solver只跑没被approve的，然后break。Verifier必定跑一次。

    问题是目前没有任何指标能看到真实的精化轮数和approve率。我准备在run()里把approved_vector.mean()（approve率指标）和实际执行的loop数记进metrics。

    1.5 Verifier几乎没动

    non-sharing配置下，Solver和Verifyer两个agent的指标是分开记的。

    • Solver：entropy 0.22 → 0.071 @310-400 → 回升 0.13，pg_loss 量级 6e-2，grad_norm 0.16→0.35
    • Verifier：entropy 全程 0.20~0.26 几乎不降，pg_loss 量级 5e-4（比 Solver 小两个数量级），grad_norm 0.41 → 0.11

    pg_loss量级差两个数量级，说明Verifier那批token上的advantage本身就接近0，导致Verifier的位移很小，分布基本没变。

    我推测原因是这个实现里的reward是traj级的，rollout_loop.py里同一条轨迹的Solver行和Verifier行被赋同一个rewards。Verifier只输出一句approve/reject，它跟最终对错的相关性远弱于Solver的解题过程，按agent_id分组归一化之后advantage方差小、均值接近0，所以梯度自然就小。

    这可能就是Dr.MAS自己在讲的他们没有去做的credit assignment问题，Dr.MAS只是把它normalize了一下，并没有真的做分解。正好是我之前的CAD-GRPO的哪个idea想做的那个点，也许这组曲线可以直接拿来当motivation。

    不过没被训动可能本身也不是什么坏事。如果Verifier初始行为已经够用了，不动反而稳定。真正要担心的是它degenerate成永远approve，那Solver就永远进不了第二轮，这个可以通过approve率指标去测。

    1.6 训练动力

    我发现训练中的entropy_loss从0.286一路掉到step 510的0.091，之后反弹到0.33~0.40并稳住。这个run entropy_coeff=0、use_kl_loss=False、use_kl_in_reward=False，对entropy是完全自由的，所以反弹肯定不是entropy bonus和KL这几个正则项拉回来的。我猜可能是回答变长（1690→1881 token，entropy是per-token平均，长尾token不确定性高）；或是reward到0.75+之后一个group里8个rollout经常全对，导致GRPO下advantage全0，没梯度，导致有效梯度样本变少变偏，第二个epoch开始重复数据。

    同时，我一开始觉得val曲线在step 690到顶之后回落，是一个轻微过拟合，之后问过Claude发现step≥500的33个点均值62.9、标准差2.2，最后一个点62.7正好落在均值上，所谓的峰值67.3只是33次噪声抽样里的最大值而已。实际上应是val在step 500之后进平台期，train reward还在慢慢涨，属于收益递减。

    还有一个坑要记一下就是由于内存受限的原因，我的entrypoint里DRMAS_MAX_ACTOR_CKPT_TO_KEEP=2，只保留了最近两个checkpoint，814步跑完磁盘上只剩step 775和800。想回头取中间某一步的checkpoint是取不到的，以后要做best-checkpoint selection要先把这个数调大。
