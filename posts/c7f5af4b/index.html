    1. Dr.MAS Verifier行为诊断

    上周to-do的第一条，让Claude给math_orchestra.run()加了approve率和实际loop数的metrics，然后在大数据平台上跑了个短作业，看Verifier有没有degenerate成永远approve。结论是没有，反而更容易拒绝了，non-sharing的Verifier训完之后差不多变成了永远reject。

    1.1 加的指标

    读代码的时候先发现了一个坑，agent_system/agent/agents/math/verifier_agent.py:81里，Verifier的输出里既没有approve也没有reject的时候（被截断或者大小写不对），是直接按approve处理的。所以如果只看approved_vector.mean()，被截断的Verifier也会被算成approve，于是我把判决拆成了三类单独记。

    • run()里记每道题实际跑了几轮Solver（loop数）和Verifier每次的判决（显式approve / 显式reject / 无判决），挂到每个agent的batch上，在ray_trainer的_validate()里按traj_uid去重后汇总成val/orchestra/，fit()里也加了train/orchestra/（这一路还没真正跑过）
    • approve_rate_on_wrong：最终答案错的轨迹里被Verifier放行的比例，永远approve的Verifier这里是1
    • approve_rate_on_correct：最终答案对的轨迹里被放行的比例

    1.2 结果

    用的是训练时的test_sampled（MATH500前50题 + AIME’24 30题 + AIME’25 30题，共110题），val_n=8，每组880条轨迹，temperature 0.6。除了两个step 814的checkpoint，还加了一组没训过的Qwen3-4B跑同一套orchestra当base，不然说不了"退化"。

    base sharing@814 non-sharing@814
    avg@8 48.5 63.7 66.9
    approve率 74.0 58.8 21.8
    reject率 26.0 41.2 78.2
    无判决 0 0.9 0
    实际loop数均值 1.26 1.41 1.78
    错误答案被放行 50.3 17.6 5.8
    正确答案被放行 99.1 82.2 29.7
    放行后正确率 65.0 89.2 91.1
    被拒重试后正确率 1.7 27.5 60.2

    发现了以下几点：

    • base的Verifier很松，错的答案一半都放过去了（50.3%），对的几乎全放（99.1%），被拒之后的重试也基本救不回来（1.7%）
    • sharing训完之后Verifier更有区分度了，错的只放过17.6%，对的还放82.2%，算是往好的方向走
    • 但是non-sharing的reject率78.2%，对的答案也只放过29.7%，基本每题都reject。MATH500前50题上最终正确率91.2%，它还是拒了66.0%，而被拒的题重试后92.8%是对的，比整体还高，拒掉的应该大多是本来就能做对的题
    • 无判决的比例几乎是0（sharing最高也只有0.9%），所以不是截断的问题，Verifier是明确输出了reject

    所以上周担心的"degenerate成永远approve，Solver进不了第二轮"没有发生，non-sharing反而有78%的题都进了第二轮。

    base在1卡和4卡上各跑了一次，approve率72.5 vs 74.0，avg@8 48.2 vs 48.5，结果是稳定的。

    同时，sharing@814在AIME’24上这次avg@8是47.5，跟上周算的训练中val的均值47.7几乎一样，论文的39.3比这个均值还是低了1.3σ左右。

    1.3 用test_score反推reject率

    max_loop_num=2时approve的轨迹是2行（Solver、Verifier），reject的是3行（多一行Solver重试），每行都记整条轨迹的0/1 reward，设N为轨迹数、C为答对数、R为被reject的数、B为被reject里最后答对的数，那么

    test_score=2C+B2N+R,avg@k=CN\text{test\_score}=\frac{2C+B}{2N+R},\qquad \text{avg@k}=\frac{C}{N} test_score=2N+R2C+B​,avg@k=NC​

    np.mean对0/1求平均就是两个整数做一次除法。完整eval（1547题×16）反推和跟这次实测对照：

    reject率 反推（完整测试集×16） 实测（110题×8）
    sharing AIME’24 65.0 61.7
    sharing AIME’25 67.7 67.5
    sharing MATH500 13.9 13.3（前50题）
    non-sharing AIME’24 30.8或88.5（两个解） 88.3
    non-sharing AIME’25 88.7 88.3
    non-sharing MATH500 63.0 66.0（前50题）

    相当于日志里只记了 test_score和avg@k两个汇总数，没有直接记录 Verifier 的reject 率。但可以利用 “0/1 求平均的结果是两个整数相除”这一点，从这两个数把 reject 率 R/N 反推出来。然后另跑一次小规模实验，直接测出 reject 率来对照，确认反推是对的。

    1.4 Verifier

    上周我根据non-sharing下Verifier的entropy全程0.20~0.26、pg_loss比Solver小两个数量级，说Verifier几乎没被训动，但这周直接测出来reject率从base的26.0%变成了78.2%，至少在行为上这个说法站不住。可能是entropy和pg_loss被前面一大段critique的token主导了，最后那个approve/reject的分布变了也看不出来(猜测)。

    还有一个混淆没排除，base这组的Solver也是没训过的，Verifier看到的解答本身就不一样，reject率变高可能有一部分是Solver的输出变了，不完全是Verifier自己变了。non-sharing两个模型是分开存的，交叉组合一下（训过的Solver配没训的Verifier，再反过来一组）就能拆开，sharing共用一个模型拆不了。

    1.5 猜想

    max_loop_num=2的时候reject只会让Solver再改一遍，而且改完不再验证，重试的正确率又不低（non-sharing是60.2%），所以Verifier错拒一次几乎不会被团队的结果reward惩罚，它的判决跟最终reward之间的联系很弱(猜测)。这跟上周1.5里说的traj级reward、Verifier拿不到有效advantage应该是同一个原因。可以跟上周的梯度曲线一起放进作为motivation之一（猜测）。

    还有一个小插曲是，我原本想把作业拆成1卡和2卡的小作业插空，结果带checkpoint的两组都在加载的时候FileNotFoundError，verl的FSDP checkpoint是按保存时的卡数分片的（model_world_size_4_rank_0~3.pt），换了卡数就找不到文件，只有不加载checkpoint的base跑成了，最后还是等4卡的作业跑完。以后resume这两个checkpoint只能用4卡，除非先合并成HF格式

    代码在experiments/drmas_overlay/，结果在experiments/results/orchestra_diag_1126238.json。

    2. AIME’24重复eval

    上周to-do的第2条。上周1.3里我拿训练中val的avg@1标准差（6.2）当σ，说sharing在AIME’24上比论文高的+12.2大概1.5~2σ，在可接受的范围内。这周把sharing的checkpoint在AIME’24上重复eval了16次，结论是+12.2不在重复eval的波动范围里，上周这个判断是错的。

    2.1 做法

    • 上周想用的step 775其实已经没有权重了，global_step_775/actor/是空的，只剩一个data.pt，是max_actor_ckpt_to_keep=2的轮转删掉的。完整留下来的是800和814（verl在最后一步也会存一次）
    • AIME’24的30题复制8份拼成一个parquet，每份的data_source改成aime24_r0~r7，val_n还是16，这样一次加载就能拿到8个独立的avg@16（data_source在这条路径上只是个标签，env打分用的是env_kwargs里的，没动）
    • launcher直接用1089597那次eval的，只改了验证文件、env.seed（0→1）、实验名和resume的step，814和800各跑一遍，作业1126291，排了21个多小时的队，4卡跑了1小时13分
    • 作业最后自动汇总的summary没解析出来（Ray给日志每行前面加了(TaskRunner pid=…)，脚本只认行首的step:），下面的数是直接从两份日志里step:814和step:800那两行指标读的。日志里只有3位小数，但avg@16一定是k/480，换算回去是唯一的

    2.2 结果

    AIME’24 avg@16，每个checkpoint 8次：

    8次avg@16 均值 标准差 范围
    step 814 46.0, 51.0, 49.4, 47.1, 48.5, 49.0, 49.0, 48.1 48.52 1.50 46.0~51.0
    step 800 49.6, 49.2, 48.5, 47.3, 49.2, 47.3, 48.5, 50.0 48.70 0.99 47.3~50.0

    pass@16的均值是79.2（814）和77.9（800），标准差都在2.4左右。

    • 同一个checkpoint重复eval，avg@16的标准差只有1.0~1.5，814和800之间也基本没差（-0.18，se 0.64）
    • 上周那次eval的51.5，这8次里一次都没到（最高51.0），比814的均值高2.9，大概+2σ，那次算是偏高的
    • 论文的39.3比814的均值低9.2，大概-6σ，8次里最低的也有46.0
    • 用重复eval的均值48.5代替单次的51.5，和论文的差距从+12.2变成+9.2，还是远在eval噪声之外

    2.3 上周的σ用错了

    上周拿来当σ的6.2是训练中avg@1的波动，每题只采1个样本，avg@16每题平均了16个样本，采样噪声差不多要除以√16=4。我还说30题的题目集方差压不掉，实则是因为拿avg@1的σ去衡量avg@16的差距，会把噪声高估好几倍。

    30题×16个样本的时候avg@16的采样标准差其实有个上限，每道题正确率都刚好50%的时候取到

    σavg@16≤13030×0.2516≈2.3%\sigma_{\text{avg@16}}\le\frac{1}{30}\sqrt{\frac{30\times 0.25}{16}}\approx 2.3\% σavg@16​≤301​1630×0.25​​≈2.3%

    这次实测的1.0~1.5也在这个范围里。1.2最后那句"论文的39.3比这个均值还是低了1.3σ左右"用的也是6.2这个σ，同样不成立。
