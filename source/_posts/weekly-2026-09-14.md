## 一、复现 Dr.MAS 和 C3 实验

### 1.1 C3 数据检查

C3 环境中缺少 MBPP+ 数据。项目读取数据时使用了不匹配的字段，导致每行除 `task_id` 和 `source` 外，其余字段都是 `null`，题目和代码等内容实际为空。另外，仓库只检查文件 SHA256 是否与 manifest 一致；如果错误文件本身的哈希也写进了 manifest，这项检查仍然会通过，因此不能验证数据语义正确。

我还发现，作者提供的 MATH 训练集和测试集中有一道完全相同的题，可能造成数据泄漏，使测试结果不可靠。我已向作者反馈并收到回复。后续需要等数据和字段问题澄清后，再判断这套结果是否适合作为比较基线。

### 1.2 Dr.MAS Qwen3-4B 评测结果

4B sharing 和 non-sharing 两个训练作业都完成了 814 step（`total_epochs=2`）。sharing 训练耗时 60.6 小时，non-sharing 耗时 71.4 小时。对应的 eval 作业也已完成，因此本周可以把 `avg@16` 和 `pass@16` 与论文表格对照。

#### 1.2.1 先统一 test_score 的统计口径

最初看到 eval 输出的 `test_score` 时，我去检查了 `verl/trainer/ppo/ray_trainer.py:884`，发现 `test_score = np.mean(rewards)` 是按 agent 行求平均的。一条轨迹里 Solver 和 Verifier 各占一行；Solver 被 reject 后还可能多一行，因此 AIME'24 上分母约为 30 道题乘以每题 2 到 3 行。这个数不能直接当作题目级准确率，需要用 `compute_pass_at_k_and_avg_at_k` 计算 `avg@k/pass@k`。

### 1.3 AIME'24 的波动与结果差异

我最开始怀疑论文是否没有使用完整的 814 步结果。论文没有明确报告训练步数，但官方脚本 `src/examples/drmas_trainer/run_math.sh` 将 `total_epochs=2` 写死，也没有设置 `total_training_steps` 上限。按该脚本执行得到 814 step，因此目前没有证据支持“论文只训到较早步骤”这个解释。

更可能的差异来源是 AIME'24 只有 30 道题，估计方差较大。训练期间 step≥500 的 33 次验证中，同一模型在 AIME'24 上的 `avg@1` 均值为 47.7、标准差为 6.2、范围为 36.7–60.0；overall `avg@1` 的均值为 62.9、标准差为 2.2。只考虑采样波动，AIME'24 的结果就能跨越 23 个百分点。sharing 的 +12.2 大约是 1.5–2 个标准差，仍可能来自小样本与采样随机性，需要再评测确认。

我也觉得只用 30 道题的 AIME'24 作为主要指标说服力有限，论文中几个百分点的差异可能受到明显噪声影响。下一步准备对保留的 step 775 checkpoint 或额外 seed 重跑 eval。

### 1.4 `episode/length` 恒为 1 的原因

![Math 环境训练曲线中的 episode/length](/img/weekly/image-20260922021854716.png)

训练曲线里的 `episode/length` 最小值、最大值和均值在 814 步内都保持为 1。起初我以为 Solver↔Verifier 的精化循环没有进入第二轮，因为配置中的 `max_loop_num=2`。检查代码后发现，`agent_system/environments/env_package/math/envs.py:23` 的 `step()` 会直接设置 `done = True`；而 `agent_system/multi_turn_rollout/rollout_loop.py:444` 中的 `episode_lengths` 只统计外层环境 step。

Solver↔Verifier 的整个循环实际在一次 `multiagent_orchestra.run()` 调用内部执行。外层 Math 环境第一步就结束，所以 `episode/length=1` 是预期行为，不能据此推断精化循环只跑了一轮。`max_loop_num=2` 下，loop 0 先由 Solver 生成并由 Verifier 审核；loop 1 只处理未获 approve 的样本，之后退出。Verifier 至少会执行一次。

目前日志没有记录真实精化轮数和 approve 率。我准备在 `run()` 中增加 `approved_vector.mean()` 和实际执行 loop 数的 metrics，再用短作业检查 Verifier 是否退化为总是 approve。

### 1.5 Verifier 的梯度明显较小

non-sharing 配置把 Solver 和 Verifier 的指标分开记录。Solver 的 entropy 从约 0.22 降到 step 310–400 附近的 0.071，之后回升到 0.13；`pg_loss` 量级约为 `6e-2`，`grad_norm` 从 0.16 增至 0.35。Verifier 的 entropy 全程约为 0.20–0.26，`pg_loss` 约为 `5e-4`，比 Solver 小两个数量级；`grad_norm` 从 0.41 降至 0.11。

这说明 Verifier 对应 token 的更新幅度较小，但具体原因还需要验证。一个可能解释是当前实现使用 trajectory-level reward：同一轨迹中 Solver 与 Verifier 行共享 reward。Verifier 只输出 approve/reject，其动作与最终答案对错的关联可能弱于 Solver 的解题过程；再按 `agent_id` 分组归一化后，Verifier 的 advantage 变化可能较小，从而产生较弱梯度。

这与我关心的 credit assignment 问题有关：Dr.MAS 对不同 agent 的信号做了归一化，但没有进一步分解团队结果。如果后续确认 Verifier 的信号确实长期接近零，这组现象可以作为 CAD-GRPO 动机的候选证据。不过 Verifier 更新较少也不一定是坏事；如果它初始策略已经足够稳定，变化小可能有利于训练。更需要排查的是它是否退化为永远 approve，导致 Solver 无法进入后续精化轮。

### 1.6 训练曲线与 checkpoint 保留

![训练过程中的 entropy 曲线](/img/weekly/image-20260922023157473.png)

训练中的 `entropy_loss` 从 0.286 降到 step 510 的 0.091，随后回升到 0.33–0.40 并趋于稳定。该 run 的 `entropy_coeff=0`、`use_kl_loss=False`、`use_kl_in_reward=False`，因此这次回升不是 entropy bonus 或 KL 项直接拉回来的。可能原因包括回答长度从约 1690 增至 1881 token、per-token entropy 受长尾 token 不确定性影响；也可能是 reward 达到 0.75 以上后，group 内 8 个 rollout 更常出现全对样本，使 GRPO advantage 为零、有效梯度样本减少。现在这些仍是待验证的解释。

我原先把 step 690 后 val 曲线回落看成轻微过拟合；复查 step≥500 的 33 个点后，均值为 62.9、标准差为 2.2，最后一个点 62.7 正好接近均值。67.3 更像这 33 次带噪评估中的一次高点。当前证据更支持 step 500 后进入平台期、训练 reward 仍缓慢上涨但收益递减，而不足以断言过拟合。

另一个实验管理上的坑是，受内存限制，entrypoint 设置了 `DRMAS_MAX_ACTOR_CKPT_TO_KEEP=2`。814 步训练结束后只剩 step 775 和 800 checkpoint，无法回取更多中间点做 best-checkpoint selection。之后要做 checkpoint 选择，需要预先提高保留数量或另行保存候选点。
